# Firebase 여행별 공동 편집

Google 로그인 후 누구나 자신의 여행을 만들고, 원하는 동행인만 초대하는 구조다. 정적 앱은 GitHub Pages, 인증·여행 데이터는 기존 Firebase 프로젝트를 그대로 사용한다. 별도 유료 API나 서버 계정은 추가하지 않는다. Firebase와 Google 지도의 사용량 제한은 각각 유지한다.

## 이미 Firebase를 설정한 사용자의 적용 순서

닉네임 기능을 추가했으므로 이전 여행별 공유 규칙을 이미 게시했어도 **현재 firestore.rules 전체 내용으로 다시 게시**한다. profiles 컬렉션이나 사용자 문서는 앱이 닉네임 저장 시 자동 생성한다. 콘솔에서 테이블을 미리 만들지 않는다.

1. 기존 앱에서 JSON 백업을 한 번 받아 두고, 편집 중인 여행 창을 닫는다. 기존 `settings/members`, `trips` 문서와 UID 배열은 삭제하거나 변경하지 않는다.
2. VS Code에서 프로젝트의 **firestore.rules**를 연 뒤 전체 내용을 복사한다. Firebase 콘솔 → **빌드 또는 데이터베이스 및 스토리지 → Firestore Database → 규칙**에서 기존 내용을 교체하고 **게시**한다. Rules Playground에서 임의로 모두 허용하는 규칙을 추가하지 않는다.
3. 프로젝트 폴더의 PowerShell에서 `git push origin main`을 실행하고 GitHub 저장소 → Actions에서 Pages 배포 성공을 확인한다. 규칙 적용 후 새 앱 배포 전까지는 옛 앱에서 저장이 거절될 수 있다. 새로고침해서 새 앱을 사용한다.
4. 본인 Google 계정으로 로그인하고 앱에서 사용할 닉네임을 정한다. 기존 사용자도 처음 한 번 설정한다. 기존 공유 여행은 원래 참여자 두 명을 유지한 새 구조로 자동 전환된다. **처음 전환한 계정이 여행장**이 된다. 서버 데이터는 원본을 보존하며 재접속으로 중복 생성하지 않는다. 먼저 본인 계정으로 전환을 완료한 뒤 친구에게 배포한다.
5. 여행 열기 → **여행 공유 → 초대 링크 만들기 → 링크 복사**를 누른다. 링크를 카카오톡 등으로 직접 전달한다. 링크는 7일 동안 유효하며 새 링크를 만들면 이전 링크는 취소된다.
6. 친구는 링크 열기 → Google 로그인 → 닉네임 설정 → **참여 요청 보내기**를 누른다. 닉네임을 정해도 원래 초대는 유지된다. 승인 전에는 여행 일정·예약·참여자 목록을 볼 수 없다. 링크 화면에는 여행 이름만 표시된다.
7. 여행장은 **여행 공유** 화면의 요청 목록에서 닉네임과 구분용 UID 끝 6자리를 확인하고 **승인**한다. 승인되면 친구의 여행 목록에 추가되고 서로 편집한 내용이 실시간 반영된다. 친구 UID를 Firebase 콘솔에 직접 넣지 않아도 된다.

신규 친구는 초대 없이도 자기 여행을 만들 수 있다. 다른 사람의 여행은 볼 수 없다. 같은 사이트에서 각 친구 모임이 별도의 여행을 운영한다. 여행당 최대 20명이며 여행장은 초대 관리·참여자 제외·여행 삭제를, 일반 참여자는 공동 편집·자신의 탈퇴를 할 수 있다. 여행장 변경은 아직 지원하지 않는다.

앱 배포만으로 규칙이 게시되지는 않는다. `여행별 공유 보안 규칙을 적용...` 메시지가 나오면 2번을 확인하고 **접근 다시 확인**을 누른다. `기존 여행을 전환하지 못했어요`가 나오면 원본이 보존된 상태다. 규칙 게시·연결 확인 후 다시 로그인한다. 기존 여행을 JSON으로 재수입하면 별도 여행이 생기므로 자동 전환과 중복해서 진행하지 않는다.

## 처음 Firebase를 설정할 때

1. 기존 프로젝트를 사용하거나 Firebase 프로젝트와 웹 앱을 만든다. Firestore 데이터베이스와 Authentication의 Google 제공자를 활성화한다.
2. Authentication → 설정 → 승인된 도메인에 `ksy980324.github.io`와 개발용 `localhost`를 추가한다. 경로와 `https://`는 넣지 않는다. 로컬 Google 로그인은 `127.0.0.1` 대신 승인한 `localhost`로 연다.
3. 웹 앱 구성 JSON을 개발 환경의 `.env.local`에서 `VITE_FIREBASE_CONFIG`에, GitHub Actions Secret에서는 `FIREBASE_WEB_CONFIG`에 넣는다. 이미 등록했다면 수정할 필요 없다. Firebase 서비스 계정 비밀 키는 프런트엔드에 넣지 않는다.
4. 위의 `firestore.rules`를 게시하고 Pages를 배포한다. 새 설치는 `settings/members` 없이도 시작할 수 있다. 그 문서는 기존 두 계정 데이터 전환에만 사용한다.
5. 친구의 Google 로그인이 OAuth 테스트 사용자 제한 때문에 차단되면 Google Cloud의 인증 플랫폼에서 앱 게시 상태 또는 테스트 사용자 설정을 확인한다. 실제 로그인 실패 코드를 함께 확인하고, Firestore 규칙을 느슨하게 바꾸어 해결하지 않는다.

## 저장 구조와 데이터 보존

- `profiles/{uid}`: 앱용 nickname과 서버 updatedAt만 저장한다. 본인만 읽고 쓸 수 있으며 전체 목록 조회와 다른 사람의 프로필 조회는 금지한다. Google 이름이나 이메일을 추가 저장하지 않는다. 닉네임은 1~20자이고 중복될 수 있으며, 권한 판정에는 UID를 사용한다.
- 로그인 후 닉네임이 없는 계정은 설정을 먼저 완료한다. 메뉴의 닉네임 변경에서 바꾸면 참여 중인 여행의 memberNames에서 본인 항목만 갱신한다. 여행 카드에 이름을 표시하기 위해 다른 계정의 프로필을 조회하지 않는다. 여행장이 다른 사람의 이름을 바꾸는 것도 금지한다. 저장·갱신 실패 시 입력과 재시도 안내를 남긴다.
- 여행 카드에는 닉네임 최대 3명과 나머지 인원수를, 상세 배너 아래에는 전체 닉네임을 표시한다. 혼자 있는 여행은 '나만 보는 여행'이다. 기존 참여자가 아직 닉네임을 설정하지 않았으면 원래 표시 이름을 유지하고 로그인 후 설정할 때 갱신한다.
- `sharedTrips/{tripId}`: 여행 `trip`, `revision`, `updatedAt`, `updatedBy`, `ownerId`, `memberIds`, `memberNames`, `inviteToken`. 목록은 현재 UID가 `memberIds`에 포함된 문서만 구독한다.
- `sharedTrips/{tripId}/requests/{uid}`: 신청자 자신의 앱 닉네임, UID, 초대 토큰, 요청 시간과 pending/approved/rejected 상태. 본인 요청과 여행장의 요청 목록만 읽을 수 있다. 닉네임은 계정 소유자가 변경할 수 있으므로 여행장은 실제 초대한 친구인지 확인한다. 요청에는 제출 당시 이름이 표시되며 승인 후 최신 이름은 신청자의 접속에서 보완된다.
- `tripInvites/{token}`: 로그인한 수신자가 정확한 토큰으로만 여행 이름·만료 정보를 확인한다. 전체 목록 조회는 금지된다. 링크는 URL fragment에 넣어 일반 HTTP 요청 경로로 보내지 않는다. 링크만으로 참여하거나 승인 없이 일정에 접근하지 못한다.
- 권한 변경과 여행 저장은 트랜잭션으로 처리하고 revision을 증가시킨다. 편집 중 다른 변경이 생기면 충돌 안내와 입력을 유지한다. 오프라인에서 서버에 쓰기가 성공했다고 표시하지 않는다.
- 기존 `trips/{tripId}`는 내용과 버전을 그대로 남기고 `migratedTo`만 추가한다. 자동 전환은 같은 ID의 `sharedTrips`를 생성하는 것과 한 트랜잭션이다. 새 여행을 삭제해도 다음 로그인 때 원본이 부활하지 않는다. 이 원본은 이전 두 계정만 읽는 보존 사본이며 새 여행의 수정은 반영되지 않는다.
- JSON 백업은 여행 내용만 담고 소유권·초대 링크·권한은 담지 않는다. 가져오면 가져온 계정 소유의 새 여행이 생기므로 다시 초대해야 한다.
- 준비물은 해당 여행의 현재 참여자 전원이 체크하면 모두 완료다. 공동 지출은 현재 참여자 기준으로 균등 정산하므로 참여자가 바뀌면 과거 지출도 다시 계산된다. 이전 참여자가 결제한 공동 지출이 남으면 잘못된 송금을 안내하지 않고 정산 확인 메시지를 표시한다.
- 탈퇴·제외된 계정의 서버 접근은 차단된다. 이미 사용자가 다운로드한 JSON이나 명시적으로 저장한 오프라인 사본을 다른 기기에서 원격 삭제할 수는 없다. 오프라인 사본은 해당 기기에서 지우며, 로그아웃 때 공유 사본을 지운다.

## 개발 검증

```powershell
npm.cmd ci
npm.cmd run typecheck
npm.cmd test
npm.cmd run build
```

보안 규칙 테스트는 Node 24.12 이상과 Java 21 이상에서 실행한다. Java를 설치한 뒤 새 PowerShell을 열고 `java -version`으로 확인한다.

```powershell
npm.cmd run test:rules
```

고정 버전 Firebase CLI를 실행하고 `demo-horangnabi` 로컬 에뮬레이터에서만 검증한다. 최초 실행은 CLI와 에뮬레이터를 다운로드한다. Firebase 로그인이나 실제 데이터베이스 접속은 필요 없다. 의도적으로 거절되는 쓰기의 PERMISSION_DENIED 로그는 테스트의 일부이며 마지막 pass/fail 결과를 본다. 테스트 포트는 8089다. GitHub Pages 빌드에서도 이 보안 검증을 실행한다.

실제 계정의 Google 로그인과 공개 Firebase에 규칙을 게시하는 작업은 로컬 에뮬레이터 테스트와 별개다. 새 규칙의 실제 게시 여부, 실제 두 휴대폰의 동기화와 초대 링크 열기는 배포 후 확인한다.
