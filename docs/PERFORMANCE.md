# 첫 진입 속도 개선

측정일: 2026-11-13. 목표는 기존 공유 여행의 권한 확인·실시간 편집을 유지하면서 불필요한 다운로드와 대기를 줄이는 것이다.

## 변경과 결과

| 항목 | 변경 전 | 변경 후 |
| --- | --- | --- |
| 첫 진입 JavaScript (원본) | 301,217 bytes | 290,457 bytes |
| 첫 진입 JavaScript (gzip) | 100,299 bytes | 92,967 bytes |
| 공유 공간 요청 | 참여자 확인 후 여행 요청 | 두 요청을 동시에 시작 |
| 저장 확인 등 메타데이터 알림 | 모든 여행을 다시 검증·새 화면 데이터 생성 | 바뀐 문서만 검증, 나머지는 재사용 |
| 한글 글꼴 | 외부 Google Fonts CSS와 글꼴 요청 | 설치된 Noto Sans KR 또는 기기의 기본 한글 글꼴 |

도시 목록과 도시 일치 검사를 장소 중심 계산에서 분리해 첫 진입 시 내려받지 않는다. 도시 선택창을 열면 필요한 코드와 함께 로드된다. gzip 크기는 약 7.3% 줄었다. Firebase SDK와 지도 SDK 자체의 용량은 이번 수치에 포함되지 않으며 별도 지연 로딩을 유지한다.

## 브라우저 비교 조건

- 실제 소스의 변경 전·후 프로덕션 빌드를 사용하고 Firebase 모듈만 모의 모듈로 대체했다. 실제 계정이나 개인 여행 데이터를 사용하지 않았다.
- 참여자 응답은 400ms, 여행 응답은 600ms로 고정했다. Chrome 헤드리스, 390px 화면, 브라우저 HTTP 캐시 비활성 상태에서 전후를 번갈아 각 5회 실행했다.
- 두 버전 모두 외부 글꼴을 차단해 공유 요청 순서의 효과를 비교했다. 서버 모의 응답 외에는 별도 네트워크·CPU 제한을 적용하지 않았다.
- 여행 카드가 DOM에 표시되는 시간의 중앙값은 **1,363.9ms → 949.0ms**였다. 요청 시작 간격은 **406.4ms → 0ms**였다. DOM 표시 시간이며 실제 사용자 화면의 페인트 시간이나 Lighthouse 점수는 아니다.
- 테스트 환경에서 외부 글꼴 연결이 차단되며 몇 초 지연되는 사례를 별도로 관찰했다. 이것을 실제 사용자 환경의 지연 수치로 해석하지 않는다.

## 정확성과 검증 범위

- 참여자·여행 요청을 함께 시작해도 두 서버 응답과 현재 계정의 참여 권한이 확인되기 전에는 여행을 표시하지 않는다. Firestore 보안 규칙은 변경하지 않았다.
- 참여자 응답 지연, 미등록 계정, 여행 변경, 참여 권한 철회, 캐시에서만 바뀐 여행이 서버 메타데이터 확인 후 반영되는 흐름을 브라우저 모의 응답으로 확인했다.
- 320·390·1280px 공유 홈의 가로 넘침 없음과 여행 생성창의 지연 로딩, 일본 선택 후 요나고 도시 목록 필터, 뒤로가기로 창 닫기를 확인했다. 새 여행을 실제 Firestore에 저장하는 테스트는 수행하지 않았다.
- 단위 테스트에서 메타데이터 알림의 데이터 재사용, 변경 문서만 검증, 삭제·재생성, 버전 변경, 잘못된 문서의 거절, 구독별 캐시 분리를 확인했다. 계정 전환·재접속 때 새 캐시를 만든다.
- 실제 두 계정 사이의 Firestore 지연, 휴대폰 터치, 지도 타일·Photon·사진 서버의 속도는 이번에 측정하지 않았다. 지도와 검색 API 호출을 줄이거나 요청 간격 제한을 해제한 변경은 없다.

## 다시 측정하기

```powershell
npm.cmd run measure:startup
```

현재 환경 설정으로 프로덕션 빌드를 메모리에서 수행해 최종 파일의 gzip 크기를 구한다. 키와 사용자 데이터는 출력하지 않는다. 첫 진입 JavaScript 파일과 정적 import만 합산하므로 CSS, 동적 import, 이미지와 외부 서버의 지연을 포함한 전체 로딩 시간과 구분해야 한다. 실제 네트워크 전송 크기는 서버의 압축 방식에 따라 달라진다.

공개 사이트 배포 후 같은 휴대폰과 네트워크에서 첫 접속과 재접속을 각각 비교하고, 여전히 느린 구간을 첫 화면·지도·사진·검색으로 구분해 다음 개선을 진행한다.
